# Version v0.4 Implementation Instructions & Agent Task Prompt

## Overview & Goal
This document provides step-by-step implementation instructions and a machine-readable task specification for **Version v0.4: Application Submission, Active Lease Locking & Database Application List Filtering** of the ASP.NET Core 10 MVC Property Management Web Application (`RentalPropertyManager`).

Building upon the v0.3 rental application wizard, v0.4 introduces:
1. **Final Application Submission Workflow**: Transitions applications from `Draft` / `Returned` to `Submitted` status after verifying that both applicant information and residence history sections pass validation.
2. **Server-Side Active Lease Collision Locking**: Verifies at submission time that the target unit does not currently have an active lease (`StartDate <= Today <= EndDate`). If an active lease exists, submission is rejected with a clear error message.
3. **Application Withdrawal**: Enables applicants to withdraw an application in `Draft`, `Submitted`, or `Returned` status (transitioning status to `Withdrawn`), locking it from further edits.
4. **Database-Filtered Application List & Dashboard**: Provides a filterable list of applications for Applicants and Property Managers where SQL `WHERE` clauses are executed directly in the database via EF Core `IQueryable` (never in memory).
5. **Strict Scope Privacy**: Applicants see strictly their own submitted/draft applications, while Property Managers can browse and filter applications across all properties.

## 2. Core Features & Deliverables for v0.4

### A. Data Models & Database Context
No new database tables are required for v0.4, but existing Entity Framework Core models and relationships are utilized:
1. **`Application`**: Uses `ApplicationID`, `UnitID`, `ApplicantUserID`, `Date`, `ApplicationStatusID`, `ManagerNotes`.
2. **`ApplicationStatus`**: Reuses lookup records (`Draft`, `Submitted`, `Returned`, `Approved`, `Denied`, `Withdrawn`, `Under Review`).
3. **`Lease`**: Reuses `LeaseID`, `UnitID`, `ApplicationID`, `StartDate`, `EndDate`, `MonthlyRent`.
4. **`ApplicantsXRef`**: Junction entity linking `ApplicationID` and `ApplicantID` for applicant query scoping.

### B. Business Logic & Validation Rules

#### 1. Application Submission Rules (`POST /Application/Submit/{id}`)
* **Eligibility Check**:
  * The application MUST be in `Draft` or `Returned` status. Submitting an application in any other status returns `HTTP 400 Bad Request`.
  * The current authenticated user MUST be the owner (`ApplicantUserID == userId` or linked via `ApplicantsXRef`).
* **Section Completeness Verification**:
  * Both Section 1 (`Applicant`) and Section 2 (`ResidenceHistory`) MUST pass model validation.
  * If `Applicant` profile is incomplete (missing `Name`, `Phone`, `Email`, or `CurrentAddress`), rejection occurs.
  * If `ResidenceHistory` list is empty, submission is rejected with: `"At least one residence history record is required before submitting."`
* **Server-Side Active Lease Lock Check**:
  * Before changing status, query `dbContext.Leases` for the target `UnitID` where `StartDate <= DateTime.UtcNow.Date` AND `EndDate >= DateTime.UtcNow.Date`.
  * If an active lease exists covering today's date, reject submission with: `"This unit currently has an active lease. Applications cannot be submitted for this unit at this time."`
* **Status Transition**:
  * On success, transition `ApplicationStatusID` to `Submitted` (lookup ID for `"Submitted"`).
  * Set `Date` (submission timestamp) to `DateTime.UtcNow`.
  * Save changes to database and redirect to Application List with a success toast notification (`TempData["SuccessMessage"]`).

#### 2. Application Withdrawal Rules (`POST /Application/Withdraw/{id}`)
* **Eligibility Check**:
  * An application can be withdrawn ONLY if its status is `Draft`, `Submitted`, or `Returned`.
  * Attempting to withdraw an `Approved`, `Denied`, or `Withdrawn` application returns `HTTP 400 Bad Request`.
  * The current authenticated user MUST be the applicant owner.
* **Status Transition**:
  * Transition `ApplicationStatusID` to `Withdrawn`.
  * `Withdrawn` is a terminal status; the application immediately becomes read-only (`IsReadOnly = true`) and cannot be edited, continued, or resubmitted.

#### 3. Database Application List Filtering Rules (`GET /ApplicationList`)
* **Strict SQL Execution (`IQueryable`)**:
  * All property and status filters MUST be applied at the database level via EF Core `.Where()` prior to calling `.ToListAsync()` or `.Select()`. In-memory filtering (`.ToList().Where(...)`) is strictly prohibited.
* **Role-Based Query Scoping**:
  * **Applicant Role (`[Authorize(Roles = "Applicant")]` or unprivileged user)**: Query filter MUST automatically append `.Where(a => a.ApplicantUserID == currentUserId)`. Applicants MUST NEVER see applications created by other users.
  * **Property Manager Role (`[Authorize(Roles = "PropertyManager")]`)**: Query evaluates across all applications in the system.
* **Filter Select Lists**:
  * `AvailableProperties`: Populated with all properties (`Id`, `Name`).
  * `AvailableStatuses`: Populated with all application statuses (`Id`, `Name`).

### D. Controllers & Endpoints (Full Route Mapping)

#### 1. `ApplicationController` updates (`[Authorize]`)

* **`POST /Application/Submit/{id}`**:
  * **Authorization**: `[Authorize(Roles = "Applicant")]`
  * **Behavior**: Validates application ownership, completeness, and active lease collision. Updates status to `Submitted` or returns HTTP 400 with error details.
  * **Return**: Redirects to `/ApplicationList` on success (`302 Found`) or returns JSON `{ success = false, message = "..." }` / re-renders Summary section with `text-danger` alerts on AJAX post.

* **`POST /Application/Withdraw/{id}`**:
  * **Authorization**: `[Authorize(Roles = "Applicant")]`
  * **Behavior**: Validates ownership and status eligibility. Updates status to `Withdrawn`.
  * **Return**: JSON `{ success = true, message = "Application withdrawn successfully." }` or Redirect to `/ApplicationList`.

#### 2. `ApplicationListController` (`Controllers/ApplicationListController.cs`)

* **`GET /ApplicationList` (`Index`)**:
  * **Authorization**: `[Authorize]` (Accessible to both `Applicant` and `PropertyManager` roles)
  * **Route Parameters**: `GET /ApplicationList?propertyId=2&statusId=1`
  * **Behavior**:
    1. Obtains current logged-in user ID via `User.FindFirstValue(ClaimTypes.NameIdentifier)`.
    2. Builds base `IQueryable<Application>` with `.Include(a => a.Unit).ThenInclude(u => u.Property).Include(a => a.ApplicationStatus).Include(a => a.Applicant)`.
    3. If user is in `Applicant` role (and not `PropertyManager`), appends `.Where(a => a.ApplicantUserID == currentUserId)`.
    4. If `propertyId.HasValue`, appends `.Where(a => a.Unit.PropertyID == propertyId.Value)`.
    5. If `statusId.HasValue`, appends `.Where(a => a.ApplicationStatusID == statusId.Value)`.
    6. Executes SQL via `.OrderByDescending(a => a.Date).ToListAsync()`.
    7. Maps records to `ApplicationListItemViewModel` list. Sets `CanEdit = (StatusName == "Draft" || StatusName == "Returned")` and `CanWithdraw = (StatusName == "Draft" || StatusName == "Submitted" || StatusName == "Returned")`.
    8. Populates `AvailableProperties` and `AvailableStatuses` select lists.
    9. Returns `View("Index", filterViewModel)`.

* **`GET /ApplicationList/GridPartial`**:
  * **Authorization**: `[Authorize]`
  * **Behavior**: Executes same database `IQueryable` filtering logic as `Index`, but returns `PartialView("_ApplicationGridPartial", filterViewModel.Applications)` for client-side AJAX filtering without full page reloads.

### F. Idempotent Data Seeding Updates (`Data/DbInitializer.cs`)

`DbInitializer.cs` MUST be updated to seed applications across **every status** idempotently using Bogus for .NET:

1. **Idempotency Guard**:
   ```csharp
   if (!dbContext.Applications.Any())
   {
       // Seed Applications across all statuses
   }
   ```
2. **Seeding Strategy**:
   * Fetch seeded units, properties, and applicant user accounts.
   * Generate test `Application` records using Bogus `Faker<Application>` covering every status name:
     * `Draft`
     * `Submitted`
     * `Returned`
     * `Approved`
     * `Denied`
     * `Withdrawn`
     * `Under Review`
   * For each `Application`, seed corresponding `Applicant` profile details (`Faker<Applicant>`) and 1–3 `ResidenceHistory` records (`Faker<ResidenceHistory>`).
   * Seed at least one unit with an active `Lease` (`StartDate = Today.AddMonths(-2)`, `EndDate = Today.AddMonths(10)`) to enable active lease collision testing.
3. **Execution Guard**:
   * Running `DbInitializer.InitializeAsync()` twice in succession MUST produce identical database row counts with 0 exceptions thrown.

## 6. Critical Red Flags & Pitfalls to Watch Out For

### 🚨 Red Flag 1: In-Memory Application List Filtering (`.ToList().Where(...)`)
* **The Problem**: Calling `.ToList()` or `await dbContext.Applications.ToListAsync()` before applying `propertyId` or `statusId` filters pulls all database applications into web server memory before filtering. On large production databases, this causes severe memory bloat and slow response times.
* **The Solution**: Construct the `IQueryable<Application>` pipeline first with `.Where(...)` clauses, and invoke `.ToListAsync()` only at the very end of query building.

### 🚨 Red Flag 2: Applicant Privacy Leak (Missing Scoping Guard)
* **The Problem**: Forgetting to append `.Where(a => a.ApplicantUserID == currentUserId)` when the logged-in user is an `Applicant` allows applicants to view other applicants' personal names, contact info, and rental history.
* **The Solution**: Always evaluate `User.IsInRole("Applicant")` in `ApplicationListController` and enforce user-level SQL filtering before returning data.

### 🚨 Red Flag 3: Inline JavaScript in Filter Bar or Grid Partial Views
* **The Problem**: Placing `<script>` tags inside `_ApplicationFilterBar.cshtml` or `_ApplicationGridPartial.cshtml`. When grid partials are refreshed via AJAX, inline scripts render as inline elements in the DOM tree, breaking browser DevTools source debugging.
* **The Solution**: Put all event handlers in `wwwroot/js/application-list.js` using event delegation on `#applicationGridContainer` and static filter selects.

### 🚨 Red Flag 4: Missing Dropdown Repopulation on Re-Render
* **The Problem**: On error or filter re-render paths, failing to repopulate `AvailableProperties` or `AvailableStatuses` causes select dropdowns to render empty or throw `NullReferenceException` in Razor views.
* **The Solution**: Encapsulate select list building in a helper method (`PopulateFilterDropdownsAsync(filterViewModel)`) and call it unconditionally before returning any view.
