# Version v0.3 Implementation Instructions & Agent Task Prompt (Single-Page Rental Application Wizard & Residence History)

## Overview & Goal
This document provides step-by-step implementation instructions and a machine-readable task specification for **Version v0.3: Single-Applicant Rental Application Wizard, Section Partials & Residence History Modals** of the ASP.NET Core 10 Property Management Application (`rental-property-manager`).

The goal of v0.3 is to build an intuitive, single-page multi-section rental application wizard for Applicants. The wizard is driven by a single unified view model (`ApplicationWizardViewModel`) and broken into three distinct section partial views:
1. **Section 1: Applicant Information** (Name, Phone, Email, Current Address).
2. **Section 3: Residence History** (List of prior residences managed via Bootstrap modal CRUD).
3. **Section 3: Summary** (Read-only review of all sections with final Submit action).

All security relies strictly on **native ASP.NET Core Identity Roles** (`Applicant` and `PropertyManager`), and application updates are restricted server-side to applications in `Draft` or `Returned` status.

### B. Business Logic & Validation Rules
1. **Single View Model Driver**:
   - The entire wizard workflow (Steps 1, 2, and 3) MUST be driven by a single unified `ApplicationWizardViewModel`.
2. **Editable vs Read-Only State Enforcement**:
   - Form controls are editable ONLY when `ApplicationStatus.Name` is `Draft` or `Returned`.
   - If the status is `Submitted`, `Approved`, `Denied`, or `Withdrawn`, the server sets `IsReadOnly = true` on the View Model, rendering display spans/text instead of editable inputs.
   - **Server-Side Enforcement**: Controller POST endpoints MUST reject save attempts if the application status is not `Draft` or `Returned` (returning `HTTP 400 Bad Request` or `HTTP 403 Forbidden`).
3. **Wizard Navigation Logic**:
   - **`Continue` Action**: Validates current step data. Saves step data to DB if valid, then increments `CurrentStep` (1 -> 2 -> 3). If invalid, re-renders current step partial view with validation errors (`HTTP 400`).
   - **`Back` Action**: Decrements `CurrentStep` (3 -> 2 -> 1) without invoking DB save or triggering model validation errors.
   - **`Submit` Action**: Available strictly on Step 3 (Summary). Transitions status from `Draft`/`Returned` to `Submitted`.
4. **Residence History Validation Rules**:
   - `MoveInDate` is required.
   - `MoveOutDate` is optional (for current residence), but if provided, server validation MUST ensure `MoveOutDate >= MoveInDate`.
5. **Bedrooms vs. UnitType Architectural Distinction**:
   - `Bedrooms` is an integer property on `Unit` (e.g., 0, 1, 2, 3+) and is **NOT** a `UnitType`.
   - `UnitType` is a category lookup entity representing dwelling styles (e.g., Studio / Efficiency, Traditional Multi-Bedroom, Loft, Townhome, etc.).

### D. Controllers & Endpoints (Full CRUD Definition)
#### `ApplicationController` (`[Authorize(Roles = "Applicant")]`)

1. **`GET /Application/Create?unitId={unitId}`**
   - Verifies target unit exists.
   - Creates a new `Application` record in `Draft` status for current logged-in user (`ApplicantUserID = currentUserId`).
   - Creates an associated `Applicant` record populated with user email and default values.
   - Redirects to `GET /Application/Wizard/{applicationId}?step=1`.

2. **`GET /Application/Wizard/{id}?step={step}`**
   - Validates that current logged-in user owns the application (`ApplicantUserID == currentUserId`). Returns `HTTP 403 Forbidden` if owned by another user.
   - Loads `ApplicationWizardViewModel` with `Applicant` and `ResidenceHistory` records.
   - Sets `IsReadOnly = true` if `Status` is NOT `Draft` or `Returned`.
   - Renders `Views/Application/Wizard.cshtml`.

3. **`POST /Application/Wizard/{id}`**
   - Validates ownership and application status (`Draft` or `Returned`).
   - Inspects `buttonAction` parameter (`"Continue"`, `"Back"`, or `"Submit"`).
   - If `Back`: Decrements `CurrentStep` and returns updated wizard view (no DB save).
   - If `Continue`: Validates current step View Model. On error, returns `HTTP 400` with re-rendered step partial displaying `text-danger` spans. On success, saves changes to `Applicant` or `Application`, increments `CurrentStep`, and returns updated step view.
   - If `Submit`: Validates all sections complete. Updates `ApplicationStatusID` to `Submitted`, sets `IsReadOnly = true`, and redirects to `Wizard` Summary view or Application List.

4. **`GET /Application/ResidenceModal?applicationId={appId}&residenceId={resId?}`** (Partial)
   - Validates application ownership and `Draft`/`Returned` status.
   - Returns `_ResidenceModal.cshtml` partial populated with `ResidenceModalViewModel` (empty for create, populated for edit).

5. **`POST /Application/SaveResidence`** (Partial/AJAX)
   - Route: `/Application/SaveResidence` (Method: `POST`, includes `@Html.AntiForgeryToken()`).
   - Validates ownership and application editable status.
   - Validates `MoveOutDate >= MoveInDate`.
   - On Validation Error (`HTTP 400`): Re-renders `_ResidenceModal.cshtml` partial with validation error spans (keeping modal open).
   - On Success (`HTTP 200`): Saves or updates `ResidenceHistory` in DB, returns JSON `{ success: true, applicationId: model.ApplicationID }`.

6. **`POST /Application/DeleteResidence/{id}`** (AJAX)
   - Route: `/Application/DeleteResidence/{id}` (Method: `POST`).
   - Validates ownership and application editable status. Deletes `ResidenceHistory` record. Returns JSON `{ success: true }`.

7. **`GET /Application/ResidenceTablePartial?applicationId={id}`** (Partial)
   - Returns re-rendered `_ResidenceTable.cshtml` partial containing updated residence history list for AJAX table refresh in Step 2.

### E. UI Shell, Partial Views & External Standalone JS Scripting

1. **Main Wizard View** (`Views/Application/Wizard.cshtml`):
   - Renders progress indicator header (Step 1 -> Step 2 -> Step 3).
   - Dynamically includes section partial view based on `Model.CurrentStep`:
     - Step 1: `<partial name="Partials/_ApplicantInfoSection" model="Model" />`
     - Step 2: `<partial name="Partials/_ResidenceHistorySection" model="Model" />`
     - Step 3: `<partial name="Partials/_SummarySection" model="Model" />`
   - Includes global modal placeholder: `<div id="residenceModalContainer"></div>`
   - References standalone script at bottom: `<script src="~/js/application-wizard.js"></script>`

2. **Partial Views (HTML ONLY—NO Inline `<script>` Tags)**:
   - `Views/Application/Partials/_ApplicantInfoSection.cshtml`: Form inputs for Name, Phone, Email, Current Address with `asp-validation-for` spans.
   - `Views/Application/Partials/_ResidenceHistorySection.cshtml`: Table listing prior residences with "Add Residence", "Edit", and "Delete" buttons, rendered via `_ResidenceTable.cshtml`.
   - `Views/Application/Partials/_SummarySection.cshtml`: Read-only review card displaying applicant info and residence history table, with "Submit Application" button.
   - `Views/Application/Partials/_ResidenceTable.cshtml`: Table partial showing residence history rows with action buttons.
   - `Views/Application/Modals/_ResidenceModal.cshtml`: Bootstrap 5 modal HTML containing residence form fields and anti-forgery token.

3. **Standalone External Client Script** (`wwwroot/js/application-wizard.js`):
   - **Zero Inline Scripts**: All client logic MUST reside inside `wwwroot/js/application-wizard.js` loaded normally by the parent page via `<script src="~/js/application-wizard.js">`.
   - **Post-Injection Wiring**: Intercepts "Add Residence" and "Edit Residence" button clicks, fetches `_ResidenceModal.cshtml` HTML via `fetch()`, injects into `#residenceModalContainer`, and explicitly calls `wireUpResidenceModal()` helper to attach `submit` event listeners.
   - **AJAX Submit Handler**: Submits residence modal form via `fetch()` with `POST`. If `HTTP 400` (HTML returned), updates modal body HTML to show `text-danger` spans. If `HTTP 200` (JSON `{ success: true }`), closes Bootstrap modal, fetches updated `_ResidenceTable.cshtml`, and refreshes the Step 2 table DOM.

### F. Mandatory Idempotent Data Seeding Updates (`Data/DbInitializer.cs`)

All seeding in `DbInitializer.cs` MUST be strictly idempotent and follow these three core requirements:

1. **Idempotent Full Database Seeding**:
   - Seed `ApplicationStatus` lookups (`Draft`, `Submitted`, `Returned`, `Approved`, `Denied`, `Withdrawn`) guarded by `if (!dbContext.ApplicationStatuses.Any())`.
   - Seed test users, property managers, applicants, properties, units, and applications in **every status** (`Draft`, `Submitted`, `Returned`, `Approved`, `Denied`, `Withdrawn`).
2. **Bogus Data Generation**:
   - Seed domain data using Bogus (`Faker<Application>`, `Faker<Applicant>`, `Faker<ResidenceHistory>`) to populate realistic applicant information and residence history records.
3. **Automated Business Logic Unit Tests**:
   - Include unit tests verifying wizard step transitions, validation rules, and status checks.

## 6. Critical Red Flags & Pitfalls to Watch Out For

1. 🚨 **Embedded Inline Scripts in Razor Partial Views**:
   - Placing `<script>` tags inside `_ResidenceModal.cshtml` or `_ApplicantInfoSection.cshtml` causes scripts to be silently ignored when injected via `innerHTML`.
   - **Fix**: All JavaScript MUST reside in `wwwroot/js/application-wizard.js` loaded on the parent `Wizard.cshtml` page, with an explicit `wireUpResidenceModal()` helper called immediately after injecting modal HTML.

2. 🚨 **Allowing Edits on Submitted or Terminal Applications**:
   - Relying on UI disabling alone allows malicious users to post HTTP requests modifying submitted applications.
   - **Fix**: Controller actions MUST validate application status server-side (`Status == Draft || Status == Returned`) before executing any database update.

3. 🚨 **Non-Idempotent Seeding & Missing Application Statuses**:
   - Running seeding without `.Any()` checks creates duplicate applications on every startup or test run.
   - **Fix**: Wrap all seed logic in `if (!dbContext.Applications.Any())` checks and ensure seeded test data includes applications in **every status** (`Draft`, `Submitted`, `Returned`, `Approved`, `Denied`, `Withdrawn`).

4. 🚨 **Multi-ViewModel Wizard Anti-Pattern**:
   - Splitting the wizard across multiple disconnected view models creates state desynchronization.
   - **Fix**: Use a single unified `ApplicationWizardViewModel` to drive all three wizard steps.

5. 🚨 **Misconfigured Modal Form Routes & HTTP Verbs**:
   - Posting to `/api/residence/` or using `PUT` instead of `POST`.
   - **Fix**: Form action MUST target `/Application/SaveResidence` using `POST`, include `@Html.AntiForgeryToken()`, use PascalCase payload property names, and omit read-only select lists.

6. 🚨 **Conflating Bedrooms with UnitType**:
   - `Bedrooms` is an integer column on `Unit` (e.g. 0, 1, 2, 3+) and is **NOT** a `UnitType`.
   - **Fix**: Keep `Bedrooms` as an integer property on `Unit` and `UnitType` as a category lookup entity representing dwelling styles.
