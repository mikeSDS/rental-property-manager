### B. Business Logic & Idempotent Seeding Engine (`Data/DbInitializer.cs`)

The database seeding routine `DbInitializer.InitializeAsync(IServiceProvider serviceProvider)` MUST execute safely on application startup and during automated test runs without duplicating records or throwing constraint exceptions.

1. **Role Seeding Idempotency**:
   - Check `await roleManager.RoleExistsAsync("PropertyManager")` and `await roleManager.RoleExistsAsync("Applicant")`.
   - Seed missing roles using `IdentityRole`.

2. **Default System Accounts**:
   - Seed default Property Manager: `manager@realestate.com` (Password: `Manager123!`, assigned `PropertyManager` role).
   - Seed default Applicant: `applicant@realestate.com` (Password: `Applicant123!`, assigned `Applicant` role).
   - Explicit check: `if (await userManager.FindByEmailAsync(email) == null)`.

3. **Lookup Data Seeding**:
   - `UnitType` lookups: Seed active types (`Studio / Efficiency`, `Traditional Multi-Bedroom`, `Loft`, `Townhome`, `Multiplex Unit`, `Penthouse`, `Mixed-Use Residential`, `Specialized Housing Unit`) with `ActiveBool = true`, and inactive type (`Legacy Efficiency`) with `ActiveBool = false`. Guarded by `if (!await dbContext.UnitTypes.AnyAsync())`.
   - `ApplicationStatus` lookups: Seed `Draft`, `Submitted`, `Returned`, `Approved`, `Denied`, `Withdrawn`, `Under Review`. Guarded by `if (!await dbContext.ApplicationStatuses.AnyAsync())`.
   - `ActionType` lookups: Seed `Submission`, `StartReview`, `CompleteReview`, `AddProperty`, `EditProperty`, `RemoveProperty`, `AddApplication`, `WithdrawApplication`. Guarded by `if (!await dbContext.ActionTypes.AnyAsync())`.

4. **Bogus `Faker<T>` Domain Data Generators**:
   - **Properties**: Use `Bogus.Faker<Property>` to seed at least 3 realistic properties (e.g. "Highland Apartments", "Oakwood Manor", "Riverfront Towers"). Guarded by `if (!await dbContext.Properties.AnyAsync())`.
   - **Units**: Use `Bogus.Faker<Unit>` to seed 10+ units across properties with varying bedroom counts (`Bedrooms` = 0, 1, 2, 3), rent values ($1,100 to $3,800), and assigned `UnitTypeID`.
   - **Applications in EVERY Status**:
     - Use `Bogus.Faker<Application>`, `Bogus.Faker<Applicant>`, and `Bogus.Faker<ResidenceHistory>` to seed applications in **ALL 6 core statuses**:
       1. `Draft`: In-progress wizard application.
       2. `Submitted`: Pending Property Manager review.
       3. `Returned`: Sent back to applicant with review comment.
       4. `Approved`: Approved application with associated 12-month `Lease`.
       5. `Denied`: Rejected application with review comment.
       6. `Withdrawn`: Application withdrawn by applicant.
     - Guarded by `if (!await dbContext.Applications.AnyAsync())`.
   - **Active Leases**:
     - For `Approved` applications, seed a `Lease` record (`StartDate = DateTime.UtcNow.Date.AddMonths(-2)`, `EndDate = StartDate.AddMonths(12)`, `MonthlyRent = Unit.MonthlyRent`).
     - Guarded by `if (!await dbContext.Leases.AnyAsync())`.
   - **Reviews & ActionHistory**:
     - For `Submitted`, `Returned`, `Approved`, `Denied`, and `Withdrawn` applications, seed corresponding `Review` and `ActionHistory` records to populate the audit timeline. Guarded by `if (!await dbContext.ActionHistories.AnyAsync())`.

## 6. Critical Red Flags & Pitfalls to Watch Out For

### 🚨 Red Flag 1: Non-Idempotent Database Startup Seeding
* **The Problem**: Calling `dbContext.Table.AddRange()` inside `DbInitializer` without wrapping in `if (!await dbContext.Table.AnyAsync())` causes primary key collisions or duplicate rows every time the application restarts or integration tests run.
* **The Solution**: Always wrap EVERY seed block in an explicit existence guard:
  ```csharp
  if (!await dbContext.Applications.AnyAsync())
  {
      // Seed Bogus applications
  }
  ```
* **Verification in Test Suite**: Integration tests MUST execute `DbInitializer.InitializeAsync()` twice in succession and assert that total row counts remain constant and no exceptions are thrown.

### 🚨 Red Flag 2: Missing Application Status Coverage in Seed Data
* **The Problem**: Seeding applications in only 1 or 2 statuses (e.g. `Draft` and `Submitted`), leaving statuses like `Returned`, `Approved`, `Denied`, or `Withdrawn` unseeded. This violates assessment requirements and causes integration tests for reviews, leases, and applicant dashboards to fail.
* **The Solution**: Use Bogus `Faker<Application>` to seed applications explicitly covering ALL 6 core statuses (`Draft`, `Submitted`, `Returned`, `Approved`, `Denied`, `Withdrawn`).

### 🚨 Red Flag 3: Embedded Inline `<script>` Tags in Partial Views
* **The Problem**: Placing `<script>` tags inside Razor Partial Views. When partial views are loaded dynamically via AJAX, inline scripts execute in global scope without being indexed under DevTools **Sources**, making client debugging impossible. Furthermore, scripts inside `innerHTML` injections fail silently in modern browsers.
* **The Solution**: Place all JavaScript in standalone `.js` files inside `wwwroot/js/`. Load scripts on parent views and use post-injection event listener wire-up functions (e.g. `wireUpReviewModal()`).

### 🚨 Red Flag 4: Conflating `Bedrooms` with `UnitType`
* **The Problem**: Treating the integer bedroom count (`Bedrooms`) as a `UnitType`.
* **The Solution**: `Bedrooms` is a separate integer property on `Unit` (`Bedrooms >= 0`). `UnitType` is a category lookup entity representing structural layouts (`Studio / Efficiency`, `Loft`, `Townhome`, etc.).
