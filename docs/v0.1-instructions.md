# Version v0.1 Implementation Instructions & Agent Task Prompt

## Overview & Goal
This document provides step-by-step implementation instructions and a machine-readable task specification for **Version v0.1: Solution Foundation, Database Context & Identity Setup** of the ASP.NET Core 10 Razor Pages Property Management Application (`RentalPropertyManager`).

---

- **Target Framework**: .NET 10 ASP.NET Core MVC and Razor Pages
- **Database**: SQL Server / Entity Framework Core 10 (Code-First Migrations)
- **Authentication**: ASP.NET Core Identity (`IdentityDbContext`)
- **Frontend Architecture**: Razor Views, Partial Views, Bootstrap 5 UI shell
- **Reference Files in Project**:
  - `PROJECT_PLAN.md` (Full version roadmap)
  - `RealEstate_objects.md` (Domain schema notes)

## 2. Core Features & Deliverables for v0.1

### A. Data Models & Database Context

#### 1. ApplicationUser
- Create `ApplicationUser : IdentityUser`
- Properties:
  - `UserType` (string or enum: `"Applicant"` or `"PropertyManager"`)
  - `CreatedAt` (DateTime, default `DateTime.UtcNow`)
- **Migration Note**: Existing migrations were generated against plain `IdentityUser`. After adding `ApplicationUser` fields, create an incremental migration (do not modify the historical `00000000000000_CreateIdentitySchema` migration) that adds `UserType` and `CreatedAt` columns to the `AspNetUsers` table.

#### 2. UnitType
- Primary lookup table for rental unit types.
- Properties:
  - `Id` (int, Primary Key)
  - `UnitTypeName` (string, required, max 100 characters)
  - `ActiveBool` (bool, default `true`)

#### 3. ApplicationDbContext
- **Current State**: Code inherits `IdentityDbContext` (non-generic).
- **Required Change**: Update to inherit `IdentityDbContext<ApplicationUser>`.
- Must include:
  - `DbSet<UnitType> UnitTypes { get; set; }`
  - Proper EF Core model configuration for UnitType (e.g., HasKey, IsRequired, HasMaxLength).

### B. Authentication, Roles & Account UX

#### 1. Identity Roles
- Ensure two roles exist in ASP.NET Core Identity:
  - `"Applicant"`
  - `"PropertyManager"`

#### 2. Account UX Strategy (Razor Pages)
- **Recommended**: Use ASP.NET Core Identity UI pre-built Razor Pages for Register/Login/Logout (scaffold with `dotnet aspnet-codegenerator identity` if not already present).
- **Alternative** (if custom UX required): Implement custom Razor Pages under `/Pages/Account` (Register.cshtml/.cs, Login.cshtml/.cs, Logout handler) using `UserManager<ApplicationUser>` and `SignInManager<ApplicationUser>`.
- **Email Confirmation**: `Program.cs` currently sets `RequireConfirmedAccount = true`. For local development, either:
  - Disable: change to `RequireConfirmedAccount = false`, or
  - Confirm via seeding: use `DbInitializer` to confirm seeded test users.

#### 3. ViewModels (if using custom Razor Pages)

**RegisterViewModel**:
```
public class RegisterViewModel
{
    [Required]
    [EmailAddress]
    public string Email { get; set; }

    [Required]
    [DataType(DataType.Password)]
    public string Password { get; set; }

    [Required]
    [DataType(DataType.Password)]
    [Compare("Password")]
    public string ConfirmPassword { get; set; }

    [Required]
    public string RoleChoice { get; set; } // "Applicant" or "PropertyManager"
}
```

**LoginViewModel**:
```
public class LoginViewModel
{
    [Required]
    [EmailAddress]
    public string Email { get; set; }

    [Required]
    [DataType(DataType.Password)]
    public string Password { get; set; }

    public bool RememberMe { get; set; }
}
```

#### 4. Registration Flow
- Upon successful user creation with `UserManager<ApplicationUser>.CreateAsync(user, password)`:
  - Call `UserManager<ApplicationUser>.AddToRoleAsync(user, roleChoice)` to assign the selected role.
  - Return success and redirect to login or dashboard page.

### C. Application Startup, Migrations & Seeding

#### 1. Automatic Startup Migrations
- Update `Program.cs` to apply EF Core migrations automatically on app startup:
  - Create a scoped service provider after `app.Build()`.
  - Call `dbContext.Database.MigrateAsync()` inside that scope.
  - Call `DbInitializer.InitializeAsync(serviceProvider)` after migrations complete.
  - Wrap in try-catch and log errors (do not crash the app if seeding fails).

#### 2. Idempotent DbInitializer
- Create a new class `Data/DbInitializer.cs` with static method `InitializeAsync(IServiceProvider)`:
  - **Create Roles** (if not exists):
    - `RoleManager<IdentityRole>.RoleExistsAsync("Applicant")` → if false, create role.
    - `RoleManager<IdentityRole>.RoleExistsAsync("PropertyManager")` → if false, create role.
  - **Seed UnitTypes** (if not exists):
    - Check if `UnitTypes` table is empty → if yes, insert:
      - `{ UnitTypeName = "Active", ActiveBool = true }`
      - `{ UnitTypeName = "Inactive", ActiveBool = false }`
  - **Optional: Seed Test Admin User** (for local development only):
    - Check if user with email `admin@rentalmanager.local` exists → if not, create with role `PropertyManager` and mark `EmailConfirmed = true`.

#### 3. Migration Strategy
- Do not modify `Data/Migrations/00000000000000_CreateIdentitySchema.cs` (historical).
- After updating `ApplicationDbContext` and `ApplicationUser`, run:
```
  dotnet ef migrations add AddApplicationUserFields
```
- This creates a new migration file that adds `UserType` and `CreatedAt` columns.
- Run `dotnet ef database update` or rely on automatic migration in `Program.cs`.

### D. UI Shell (`_Layout.cshtml`)

Update the shared layout to include:

1. **Bootstrap 5 Navbar** with:
   - Application title: `Rental Property Manager`
   - Authenticated user display:
     - Show user email and role badge (e.g., "Applicant" or "Property Manager")
     - Use Razor conditionals: `@if (User.Identity.IsAuthenticated) { ... }`
   - Conditional links:
     - If authenticated: show user menu (Profile, Logout)
     - If not authenticated: show Register / Login links
   - Use Identity UI `SignInManager` or `UserManager` for role/email display.

2. **Toast/Alert Container**:
   - Add a placeholder div for flash messages / toast notifications (e.g., "User registered successfully").

Example snippet:

## 3. Automated Test Suite (v0.1)

Create test project `RentalPropertyManager.Tests` (xUnit) with the following test classes:

### 1. Unit Tests: Registration Role Assignment
**File**: `Tests/RegistrationRoleAssignmentTests.cs`
- **Test**: When a user registers with `RoleChoice = "PropertyManager"`, the user is added to the `PropertyManager` role.
- **Test**: When a user registers with `RoleChoice = "Applicant"`, the user is added to the `Applicant` role.
- Mock `UserManager<ApplicationUser>` and verify `AddToRoleAsync` is called with the correct role string.

### 2. Integration Tests: DbInitializer Idempotency
**File**: `Tests/DbInitializerTests.cs`
- Use `WebApplicationFactory<Program>` to host the app with a test database.
- **Test**: Run `DbInitializer.InitializeAsync(serviceProvider)` twice in succession; verify no duplicate-key or constraint exceptions occur.
- **Test**: After running `DbInitializer`, roles `Applicant` and `PropertyManager` exist in `RoleManager`.
- **Test**: After running `DbInitializer`, `UnitTypes` table contains exactly two records: `"Active"` and `"Inactive"`.
- Optionally verify seeded test admin user email is confirmed.

### 3. Authorization Tests: Role-Protected Pages
**File**: `Tests/AuthorizationTests.cs`
- Use `WebApplicationFactory<Program>` to test HTTP responses.
- **Test**: Pages/actions marked with `[Authorize(Roles = "PropertyManager")]` return 401/403 or redirect when accessed by unauthenticated users.
- **Test**: Pages/actions marked with `[Authorize(Roles = "PropertyManager")]` return 401/403 or redirect when accessed by users in the `Applicant` role.
- **Test**: Pages/actions marked with `[Authorize(Roles = "PropertyManager")]` return 200 OK when accessed by users in the `PropertyManager` role.

### Test Setup & Notes
- Add the following file to enable `WebApplicationFactory<Program>`:
```
  // RentalPropertyManager/Program.ForTests.cs
  public partial class Program { }
```
- For test database isolation, configure the test web app to use a test SQL instance or an in-memory database (see integration test setup).
- Install packages: `Microsoft.AspNetCore.Mvc.Testing`, `xunit`, `xunit.runner.visualstudio`.

## 7. Summary: Changes Made to Original Document

This section documents what was changed from the original MVC-focused plan to the Razor Pages-focused plan aligned with the actual codebase.

### A. Application Architecture (Section 1)
**Original**: "ASP.NET Core MVC" with "Razor Views, Partial Views"  
**Changed to**: "ASP.NET Core Razor Pages"  
**Reason**: The project uses Razor Pages (`Program.cs` maps `app.MapRazorPages()`), not Controller-based MVC.

### B. DbContext Type Clarification (Section 2.A.3)
**Original**: "Inherits from `IdentityDbContext<ApplicationUser>`" (assumed/stated)  
**Changed to**: Explicitly noted that current code uses **non-generic** `IdentityDbContext` and **must be updated** to `IdentityDbContext<ApplicationUser>`.  
**Reason**: The project's `Data/ApplicationDbContext.cs` currently inherits from `IdentityDbContext` (non-generic), which cannot store custom user properties like `UserType` and `CreatedAt`. This is a breaking change that requires a new migration.

### C. Migration Strategy (Section 2.C.3)
**New section added**: Migration compatibility note  
**Added guidance**: Do not modify the historical `00000000000000_CreateIdentitySchema.cs`. Instead, create an incremental migration (`AddApplicationUserFields`) to add `UserType` and `CreatedAt` columns to the `AspNetUsers` table.  
**Reason**: Best practice for EF Core and maintains database audit trail. Modifying historical migrations causes data loss.

### D. Email Confirmation Blocker (Section 2.B.2)
**New guidance added**: `Program.cs` currently sets `RequireConfirmedAccount = true`, which blocks login.  
**Added two solutions**:
  1. Disable for development: `RequireConfirmedAccount = false`
  2. Seed confirmed users in `DbInitializer`

**Reason**: Without addressing this, any user trying to log in will fail with "Invalid login attempt" even with a correct password, blocking local development and testing. This is a critical issue that must be handled upfront.

### E. Account UX: From Controller to Razor Pages (Section 2.B)
**Original**: "Implement `AccountController` with Register (GET/POST), Login (GET/POST), Logout (POST)"  
**Changed to**: 
  - **Recommended**: Scaffold ASP.NET Core Identity UI Razor Pages
  - **Alternative**: Custom Razor Pages under `/Pages/Account` using PageModels

**Reason**: Razor Pages project should use Razor Pages (not Controllers) for consistency and alignment with project architecture.

### F. Test Suite Architecture (Section 3)
**Original**: "Unit Tests (`AccountControllerTests`)" — implied unit testing of a Controller  
**Changed to**:
  - "Unit Tests: Registration Role Assignment"
  - Added concrete test file names and scenarios
  - Added requirement for `Program.ForTests.cs` partial class

**Reason**: Razor Pages use PageModels, not Controllers. Top-level statements in `Program.cs` require a partial `Program` class to work with `WebApplicationFactory<Program>` in tests.

### G. UI Shell Example (Section 2.D)
**Original**: High-level description only  
**Changed to**: Added complete Bootstrap 5 navbar code snippet showing:
  - User email and role display using `User.IsInRole()`
  - Conditional rendering for authenticated vs. unauthenticated users
  - Proper form-based logout using POST to `/Identity/Account/Logout`

**Reason**: Clear implementation guidance with working code accelerates development and reduces ambiguity.

### H. Test Database Handling (Section 3)
**New guidance added**: Test suite should use separate test database or in-memory database to avoid corrupting development data.  
**Reason**: Integration tests should be isolated from development data.

### I. Deliverables Checklist (Section 5)
**New section added**: Complete checklist of files to create/modify and validation steps.  
**Reason**: Provides clear tracking and verification of all work items.
